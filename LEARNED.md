# LEARNED — [DuckDB та Hot/Cold Storage Architecture]

## Засвоєно в процесі виконання
- DuckDB - це embedded OLAP база даних, оптимізована для аналітичних запитів, а не для транзакційної обробки (OLTP)
- Column-oriented storage зберігає дані по стовпцях, що робить агрегаційні запити (SUM, COUNT, GROUP BY) значно швидшими
- DuckDB не потребує окремого сервера - працює як SQLite, всередині додатку, що спрощує deployment та зменшує operational overhead
- Hot/Cold storage pattern дозволяє розділити навантаження: свіжі дані (hot) для операційних запитів в PostgreSQL, старі дані (cold) для аналітики в DuckDB
- SQLAlchemy інтеграція з DuckDB можлива через duckdb-engine, але має обмеження - деякі операції потребують сирого SQL
- Різні SQL діалекти між PostgreSQL та DuckDB
- Архівація даних через worker дозволяє автоматично переміщувати старі дані з hot в cold storage без downtime
- Формат дат критично важливий при роботі з двома БД - потрібна уніфікація через SQL функції (strftime, date casting)

## Плюси / Мінуси / Трейд-офи

**Плюси**
- Швидкість аналітичних запитів - column-oriented storage робить GROUP BY та aggregations значно швидшими
- Компресія даних - стовпчикове зберігання дозволяє ефективно стискати схожі дані
- SQL-сумісність - підтримує стандартний SQL, легко перейти з інших БД
- Можливість читати Parquet файли напряму - гнучкість для data pipelines
- Зменшення навантаження на операційну БД - PostgreSQL не перевантажена історичними даними
- Оптимізація під use case - кожна БД робить те, що вміє найкраще
- Можна незалежно масштабувати hot і cold storage
- Простіші backup стратегії cold data рідко змінюється, можна backup рідше

**Мінуси**
- Менша екосистема порівняно з PostgreSQL/MySQL - менше інструментів, плагінів
- SQLAlchemy інтеграція неповна - деякі операції потребують сирого SQL, не все підтримується сумісно
- Різні SQL функції** - func.date() vs func.strftime() створює додаткову складність
- Складність створення схеми через SQLAlchemy - Base.metadata.create_all() не завжди працює коректно
- Додаткова складність потрібно підтримувати дві БД, синхронізувати схеми
- Складніші запити потрібно query обидві БД та merge результати
- Testing складніше потрібно setup обидві БД в тестах

**Коли використовувати / коли уникати**
- Використовувати, якщо потрібна аналітична БД без окремого сервера, аналітичні запити з багатьма GROUP BY  
- Уникати, якщо потрібна висока пропускна здатність з одночасними запитами
- і потрібна аналітика в реальному часі за секунди. Потрібна 100% функціональна сумісність з 
- PostgreSQL через SQLAlchemy
